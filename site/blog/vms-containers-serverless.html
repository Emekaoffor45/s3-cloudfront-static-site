What I'm actually running, after a lecture on VMs and serverless

Week 2 of my Scalable Advanced Software Solutions module (COM769, part of my MSc at Ulster in Birmingham) was about where your code runs: on a virtual machine, in a container or as a serverless function. The slides use Azure. My own projects are on AWS, but the ideas are the same.

The bit I wrote down was about billing. With normal hosting you pay for a block of time, so a website that gets one visit a day still costs you the full day. With serverless you pay for the time your code runs and nothing when it isn't running. If a function runs once a day for two minutes, that's what you get billed for.

After the lecture I logged into AWS to see which of these I'm using.

My link shortener is on a VM. It's a small Flask app on an EC2 instance, with the short codes stored in MySQL on RDS. Because it's a VM, the operating system is mine to look after. I patch it, and if the app stops in the middle of the night it stays stopped until I notice. It also costs me the same on a day when nobody clicks a link as on a busy one, which is the one-visit problem from the slide. And if it ever needed to handle a lot more traffic, I'd have to add more instances and put a load balancer in front of them.

My portfolio site works differently. It's HTML files in a private S3 bucket with CloudFront in front, and when I push to GitHub a workflow copies the files up and clears the cache. There's no machine of mine anywhere in that. The lecture probably wouldn't call it serverless, because none of my code runs anywhere, but the billing follows the same idea and a quiet day costs close to nothing.

While I was in the console I found something I'd forgotten about. A CloudWatch alarm called webserver was still checking CPU usage for an Auto Scaling group I had deleted after an earlier exercise. I'd assumed that removing the servers removed everything attached to them. It didn't, and the alarm is now on my list to clear out when I finish the monitoring setup for the portfolio.

Containers are the one I haven't used yet. From the slides, a container doesn't come with an operating system for you to manage, and containers are meant to be started and stopped quickly as demand goes up and down, which is what you want for something that has to scale. My plan is to put the link shortener in Docker, get it running on my laptop, and then work out where to run it on AWS.
