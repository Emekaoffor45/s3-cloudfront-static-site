A lecture on VMs, containers and serverless, and what I found in my own AWS account

Week 2 of my cloud module was about where code actually runs. I went home and checked where mine runs.

I'm doing an MSc in Computer Science and Technology with Business Development at Ulster University in Birmingham. One of the modules is COM769, Scalable Advanced Software Solutions. The week 2 lecture covered virtual machines, containers and serverless. The examples are all Azure, but the ideas carry straight over to AWS, which is where my own projects live.

One slide stayed with me. It said traditional hosting bills you for a block of time, so even if your website gets one visitor a day, you still pay for the whole day. Serverless only bills for the time your code is actually running.

So I went through what I have running and what it costs me to keep it there.

The URL shortener is a VM

My link shortener is a Flask app on an EC2 instance. It takes a long URL, makes a short code, saves it in a MySQL database on RDS, and redirects when someone visits the short link.

EC2 is a VM. The lecture describes VMs as the option for when you need full control of the operating system, and that control is real, but so is the work that comes with it. I'm the one who patches the instance. If the Flask process dies, nobody restarts it except me. And the instance costs the same whether a hundred people use the shortener in a day or nobody does, which is exactly the "one hit a day" problem from the slide.

While I was looking, I also noticed my RDS security group lets my own IP address in, because I wanted to run queries from my laptop. The week 3 lecture on N-tier architecture says the database should only accept connections from the tier above it. Mine accepts connections from my house too. That's going on the fix list.

This site has no server at all

The site you're reading is a set of static files in a private S3 bucket, with CloudFront in front of it. There's no instance, so there's nothing to patch and nothing to restart. Every push to the main branch runs a GitHub Actions workflow that signs in to AWS with OIDC (so no access keys are stored in GitHub), syncs the files to the bucket and clears the CloudFront cache. The two commands that do the actual work: 

aws s3 sync ./site s3://devops-journey-site --delete

aws cloudfront create-invalidation \
  --distribution-id E485VDAP1XU8G \
  --paths "/*"

Strictly speaking, this isn't serverless in the sense the lecture means, because none of my code runs on the server side. But it follows the same idea. I don't reserve a server, and what I pay depends on how much the site actually gets used.

The alarm I forgot about

Recently I started setting up CloudWatch monitoring for this site. The first thing I found wasn't anything to do with the site. It was a CPU alarm called webserver, set up for an Auto Scaling group of web servers from an earlier exercise. I had deleted that group a while before. The servers were gone, but the alarm was still there, watching CPU on machines that didn't exist.

Deleting the Auto Scaling group didn't delete the alarm I'd made for it. It's a small thing and it wasn't costing me much, but it's the sort of leftover that piles up in a real account if nobody's checking.

Containers are next

Containers are the one of the three I haven't used yet. The lecture's point is that you don't manage an operating system for a container, and they're built to be started, stopped and scaled out quickly in a way VMs aren't. Docker is the usual engine.

So the plan is to put the URL shortener in a Docker container, get it running locally first, and then work out where to run it on AWS. I'll write that up here when it's done, including whatever goes wrong.
