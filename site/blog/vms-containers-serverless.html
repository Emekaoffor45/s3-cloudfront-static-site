Two workloads in my AWS account: EC2 versus S3 and CloudFront

I run two things on AWS at the moment. They sit at opposite ends of how much infrastructure you have to manage yourself.

The link shortener on EC2

A Flask app on a single EC2 instance. It takes a long URL, generates a short code, stores the mapping in MySQL on RDS and redirects when someone requests the short link.

On EC2 I'm responsible for everything from the operating system up. That means OS patches and keeping the Flask process alive. Unless I add a process manager or health checks, a crash means downtime until I notice. The instance is billed for as long as it's running, so it costs the same with zero requests as with ten thousand.

Scaling it out would need an Auto Scaling group with a load balancer in front. The app itself is in reasonable shape for that, because it keeps no state of its own. Every short code lives in RDS, so any instance could serve any request. The database would become the limit long before the web tier did.

The portfolio on S3 and CloudFront

This site is static HTML in a private S3 bucket. CloudFront serves it over HTTPS on agurichard.com with an ACM certificate, and reads from the bucket through origin access control, so the bucket itself is never public.

Deployment is a GitHub Actions workflow that runs on every push to main. The job assumes an IAM role through GitHub's OIDC provider, so there are no AWS access keys stored as repository secrets. The two commands that do the work: 

aws s3 sync ./site s3://<bucket> --delete

aws cloudfront create-invalidation \
  --distribution-id <distribution-id> \
  --paths "/*"

--delete removes anything from the bucket that's no longer in the repo, which matters when pages get renamed or moved. The invalidation clears CloudFront's cached copies so changes show up straight away. Invalidating /* on every deploy is the blunt option, but a wildcard counts as a single path and AWS gives you the first 1,000 invalidation paths each month free, so for a site this size it costs nothing.

There's no server to patch, and cost follows requests and storage instead of uptime.

An orphaned alarm

While setting up CloudWatch monitoring for the portfolio, I found an alarm called webserver still tracking CPU for an Auto Scaling group I had deleted after an earlier exercise. Deleting the group didn't delete the alarm, because I'd created it separately. It costs very little, but it's noise in the console and would be noise in any alerting built on top of it. It's on the clean-up list.

Next: containerising the shortener

The plan is a Docker image for the Flask app, with the database settings passed in as environment variables instead of living on the instance. I'll run it locally against RDS first, then decide between ECS on Fargate and App Runner for hosting it, which would take OS patching off my list entirely.
